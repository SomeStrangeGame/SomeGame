# Integration and handoff protocol

Читайте этот документ при изменении общего контракта, завершении межпроектной
работы, подготовке commit или общей интеграционной проверке.

## Атомарная передача

- Работа делится на независимо проверяемые блоки с точными путями и
  зависимостями.
- `ready-for-integration` означает, что локальный scope завершён; ожидаемые
  общие проверки перечислены отдельно.
- Общий контракт интегрируется раньше зависимых проектов; циклические ожидания
  запрещены.
- Commit включает только проверенный scope и не захватывает чужой dirty tree.
- Общая проверка выполняется после объединения зависимых изменений и только
  минимальным changed-path gate.

## Изменение общего контракта

До правки зафиксировать владельца, входы/выходы, совместимость, затронутые
projects и порядок миграции. Обновить код, первичный нормативный документ,
memory decision и routing в одном scope. Project-specific исключение не
становится глобальным hardcode без отдельного решения.

## Handoff

Запись содержит:

```markdown
## <UTC time> — <agent_id> — <status>

Task: <кратко>
Changed: <пути и результат>
Validation: <команды и результат>
Pending / risks: <остаток или none>
Suggested next step: <действие или none>
```

Не помещать секреты, полные логи, generated dumps и историю рассуждений.
`HANDOFF.md` — актуальный снимок, не вечный журнал. При 120 строках завершённые
записи без потери текста переносятся под lock в датированный
`archive/reports/CoordinationHandoffHistory-*.md`; незавершённые риски остаются.

Корректный docs-only fast path не меняет контракты и не создаёт handoff-запись.
Если документационная правка требует передачи результата другому потоку, это
уже обычный scope, а не fast path.

## Checkpoint и перезапуск чата

Автоматическая compaction текущего диалога сама по себе не требует нового чата:
текущий чат продолжает задачу. Новый чат имеет смысл на атомарной границе, если
пользователь явно просит перезапуск, начинается независимая следующая фаза либо
накопленная история мешает устойчиво удерживать точный scope и evidence.

Перезапуск запрещён во время активной команды, Unity/build/ADB-процесса,
ожидания approval или с удерживаемым write-lock. Перед передачей текущий чат:

1. Доводит текущий атомарный шаг до safe checkpoint и останавливает только свои
   процессы.
2. Проверяет scoped diff/status и сохраняет полезные логи на диске.
3. Пишет компактный handoff: цель, выполнено, точные изменённые пути,
   validation, незавершённый шаг, blockers и одну следующую команду.
4. Помечает agent record `paused-for-chat-restart` и освобождает собственные
   request/write-lock; ownership не переносится между чатами автоматически.
5. Новый чат открывается в saved project `SomeGame`, читает обязательный core,
   memory и handoff, перепроверяет Git/FIFO, создаёт новую request и заново
   получает lock перед продолжением.

Стартовый prompt нового чата должен быть коротким: «Продолжи `<scope>` из
актуального `Docs/AI/CoordinationRuntime/HANDOFF.md`; project root — `SomeGame`;
перепроверь текущие файлы/Git/FIFO и выполни указанный next step». Полную историю
старого диалога, логи и chain-of-thought в prompt не копировать. Новый чат
создаётся только по явной просьбе пользователя; протокол не запускает его
самостоятельно.

## Финальная интеграция

1. Перечитать active scopes, handoff и полный Git status.
2. Проверить зависимости и точный состав diff/commit.
3. Выполнить minimal plan/verify, затем только оставшиеся Editor/Player/manual
   gates.
4. Зафиксировать evidence и реальные ограничения.
5. Разбить проверенный diff на атомарные commits; каждый commit должен иметь
   одну цель и не захватывать чужой или generated scope.
6. Пока собственные agent/request/write-lock records остаются untracked,
   опубликовать commits канонической командой:

   ```bash
   Tools/somegame git-publish --agent-id <lock-owner> \
     [--ssh-key <local-key-path>]
   ```

   Команда публикует `HEAD` в `origin/main`, только если remote не впереди и
   дерево чисто кроме собственных runtime records. Она не выполняет
   pull/rebase/merge/force-push; расхождение разбирается отдельным явным scope.
   SSH-ключ остаётся локальным и никогда не добавляется в commit.
7. Сверить возвращённые `localSha` и `remoteSha`, записать evidence в handoff,
   завершить agent record и удалить только собственные request/write-lock.
8. Если итоговая handoff/agent запись образует отдельный commit, получить новую
   короткую FIFO-заявку и повторить ту же команду; не оставлять документированный
   результат только локально.
9. Только после подтверждённого remote SHA считать публикацию завершённой.

Если интеграционный случай здесь не покрыт, остановить изменение контракта,
зафиксировать риск в handoff и дополнить этот действующий протокол.
