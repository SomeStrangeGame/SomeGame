# Координация параллельного рефакторинга

Этот документ — общая точка входа для чатов и разработчиков, которые
одновременно меняют Game, Content SDK и атомарные контентные Unity-проекты.

Цель — не допустить, чтобы один поток работы перезаписал изменения другого,
вернул удалённую архитектуру или принял временное состояние соседнего проекта
за окончательный контракт.

## Текущее основание

- Репозиторий: `SomeGame`.
- Ветка на момент создания документа: `grandChange`.
- Базовый commit на момент создания: `c6c7853b`.
- Общий pipeline находится в `Packages/NovelsContentSdk` и
  `Tools/novels-tools`.
- Контентные проекты находятся в `Projects/novels-*`.
- Рабочее дерево может содержать незакоммиченные изменения нескольких чатов.
  Нельзя удалять или откатывать незнакомые изменения только потому, что они не
  относятся к текущей задаче.

## Обязательное правило для каждого чата

Перед изменениями чат должен:

1. Прочитать этот документ.
2. Проверить `git status --short`.
3. Объявить свою область владения в отдельном статус-файле.
4. Не менять файлы, уже заявленные другим активным потоком, без явного
   согласования.
5. После работы обновить только собственный статус-файл.

Поток не ждёт завершения соседнего потока в состоянии `active`. Закончив свою
изолированную часть, он фиксирует отложенные проверки и переводит себя в
`ready-for-integration`. Зависимости и порядок ожидания принадлежат общей
очереди, а не статусу рабочего потока.

Общий документ следует менять лишь при изменении архитектурного контракта.
Текущий прогресс отдельных задач сюда постоянно добавлять не нужно: иначе сам
координационный файл станет источником конфликтов.

## Статус-файлы потоков

Каждый параллельный поток создаёт рядом отдельный файл:

```text
Novels/Docs/AI/ParallelWork.<scope>.md
```

Примеры:

```text
ParallelWork.pipeline.md
ParallelWork.catalog.md
ParallelWork.tzm.md
ParallelWork.zdm.md
ParallelWork.game.md
```

Шаблон статус-файла:

```markdown
# Parallel work: <scope>

- Статус: active | ready-for-integration | integrated
- Ветка: <branch>
- Базовый commit: <hash>
- Ответственный поток: <chat/task description>
- Последнее обновление: YYYY-MM-DD

## Разрешённая область

- `точные/пути/**`

## Не изменять

- `чужие/пути/**`

## Изменённые контракты

- Нет.

## Выполнено

- ...

## Проверено

- команда — результат

## Требуется при интеграции

- ...
```

Если статус-файл уже существует, новый чат сначала читает его и продолжает
работу в заявленных границах либо создаёт файл с более узким scope.

Значение статуса:

- `active` — поток прямо сейчас меняет файлы своей области;
- `ready-for-integration` — локальная работа завершена, даже если общая
  компиляция или сборка ждёт других изменений;
- `integrated` — общий координатор проверил результат вместе с зависимостями;
- `paused` — поток остановлен до завершения локальной части и должен быть явно
  возобновлён.

Нельзя оставлять `active` только потому, что ожидается общий SDK, свободный
Unity Editor или финальная интеграционная проверка.

## Расширение области владения

Координационный механизм позволяет потоку расширить работу за пределы одного
проекта, но не даёт автоматического права менять соседние области. Расширение
оформляется до первого изменения файлов и действует только для перечисленных
путей.

Порядок расширения:

1. Прочитать статус-файлы текущих владельцев затрагиваемых областей.
2. Убедиться, что требуемые файлы не принадлежат другому потоку со статусом
   `active`.
3. Создать отдельный `ParallelWork.<scope>.md` для межпроектной задачи либо
   явно дополнить собственную область, если все изменения остаются внутри
   одного проекта.
4. Перечислить точные файлы или минимальные подкаталоги, ожидаемый контракт и
   проверки. Заявка на широкий каталог вроде `Packages/**` без необходимости
   недопустима.
5. Получить обычный runtime `write-lock`. Статус-файл описывает владение, но
   сам по себе не разрешает запись.
6. После локальной проверки перевести новый scope в
   `ready-for-integration`, освободить runtime lock и передать результат через
   `HANDOFF.md`.
7. После общей интеграционной проверки вернуть владение исходному потоку либо
   пометить временный scope как `integrated`.

Один файл не может одновременно входить в разрешённую область двух потоков со
статусом `active`. При пересечении приоритет имеет ранее объявленный активный
владелец. Более поздний поток сужает scope, ждёт явной передачи или описывает
запрос без изменения файла.

Чужой статус-файл не редактируется для получения владения. Передача
подтверждается владельцем в его handoff либо отдельным новым scope после того,
как прежний статус перестал быть `active`.

### Временный межпроектный scope

Сквозная задача, затрагивающая проект и несколько общих файлов, получает
отдельный статус вместо расширения одного проектного потока на весь SDK.

Например, перенос проверки размера Catalog в общий pipeline оформляется как:

```text
ParallelWork.bundle-audit.md

Разрешено:
- Packages/NovelsContentSdk/Editor/ContentBundleAudit.cs
- Packages/NovelsContentSdk/Editor/ContentPipeline.cs
- Projects/novels-catalog/Assets/Editor/**
- Novels/Docs/AI/ParallelWork.bundle-audit.md

Не разрешено:
- остальные Packages/**
- Tools/**
- Projects/novels-tzm/**
- Projects/novels-zdm/**
- Game runtime
```

Такой scope обязан указать:

- исходный commit;
- владельца и зависимые потоки;
- точные входные и выходные контракты;
- файлы, которые будут созданы, изменены или удалены;
- локальную проверку;
- общую проверку, необходимую при интеграции;
- условие возврата владения.

### Атомарные блоки внутри расширенного scope

Расширенный scope не превращает несколько изменений в один большой diff.
Работа делится на блоки, каждый из которых можно независимо проверить,
интегрировать и отменить без возврата соседних блоков.

Пример последовательности:

```text
1. общий audit API
2. подключение к pipeline
3. миграция Catalog
4. удаление локального audit-кода
5. интеграционная проверка
```

Для каждого блока в status-файле фиксируются изменённые пути, проверка и
зависимость от предыдущего блока. Атомарность определяется не количеством
файлов и не размером всей задачи, а независимостью проверки, интеграции и
отката каждого блока.

Расширение не разрешает:

- брать весь SDK ради одного метода;
- менять общий контракт без записи в status-файле;
- переносить локальную особенность проекта в общий hardcode;
- удерживать runtime lock между независимыми блоками или во время ожидания;
- включать чужие незавершённые изменения в свой commit или handoff.

## Очередь интеграции

Единственный координатор ведёт файл:

```text
Novels/Docs/AI/ParallelWork.queue.md
```

Рабочие потоки этот файл не редактируют. Они только обновляют собственные
status-файлы. Координатор последовательно переводит элементы очереди:

```text
queued -> running -> done
                  -> blocked
```

`blocked` обязательно содержит конкретную причину и зависимость. Он не
превращается обратно в `running` автоматически по бесконечному polling: перед
продолжением координатор повторно читает status-файлы и фиксирует новое
основание.

Файл `ParallelWork.queue.md` описывает архитектурный порядок интеграции, но не
является взаимным исключением. Для фактического владения правом записи
используется атомарная runtime-очередь, описанная ниже.

Очередь задаётся как ориентированный граф без циклов. Рабочий поток может
зависеть от общего контракта для финальной проверки, но общий контракт не ждёт
статуса `integrated` этого же потока. Правильная последовательность:

```text
локальная работа проекта
  -> ready-for-integration
  -> общий pipeline
  -> интеграционная проверка проекта
  -> integrated
```

### Эксклюзивный Unity-ресурс

В любой момент Unity использует только один элемент очереди. Перед запуском
координатор проверяет активные процессы. Если Editor занят человеком или другим
потоком, задача получает `blocked: unity-in-use`; остальные read-only и
не-Unity задачи могут продолжаться.

Не следует запускать бесконечный shell-loop, ожидающий изменения Markdown.
Ожидание выполняется ограниченными проверками состояния, а после остановки
соседнего процесса пользователь или координатор явно возобновляет очередь.

## Операционная очередь и атомарная блокировка

Runtime-состояние координации хранится в:

```text
Novels/Docs/AI/CoordinationRuntime/
  requests/
  active/write-lock/
  agents/
  HANDOFF.md
```

Markdown-статус сам по себе не считается блокировкой. Единственное основание
для записи — успешно созданный атомарной операцией каталог
`active/write-lock`.

Перед любым изменением рабочего дерева, запуском Unity, сборки, генератора,
форматтера или команды, способной переписать файлы, чат должен:

1. Выбрать стабильный уникальный `agent_id` на всё время задачи.
2. Создать `agents/<agent_id>.md` с задачей, областью и ожидаемыми файлами.
3. Атомарно создать заявку
   `requests/<UTC timestamp>-<agent_id>/request.md`.
4. Дождаться, когда заявка станет первой в лексикографическом порядке и
   `active/write-lock` будет отсутствовать.
5. Атомарно создать `active/write-lock`, записать туда `owner.md` и повторно
   проверить, что заявка всё ещё первая.
6. Только после этого менять файлы или запускать тяжёлый процесс.

`owner.md` содержит имя заявки, `agent_id`, задачу, область, время получения и
`heartbeat_utc`. Heartbeat обновляется не реже одного раза в пять минут и перед
долгой командой.

Создание и обновление собственной заявки, agent-записи, lock и handoff-записи
не требует отдельной позиции в очереди. Нельзя менять или удалять runtime-файлы
другого чата.

### Освобождение очереди

Перед освобождением владелец:

1. Выполняет соразмерную проверку и повторно смотрит `git status`.
2. Добавляет результат в `CoordinationRuntime/HANDOFF.md`.
3. Удаляет только собственную заявку.
4. Удаляет только принадлежащий ему `active/write-lock`.
5. Помечает собственную agent-запись как `completed`, `yielded`, `blocked` или
   `abandoned`.

Нельзя держать lock во время ожидания пользователя, разрешения, соседнего
проекта или внешнего сервиса. В таком случае состояние фиксируется, lock
освобождается, а после продолжения задача снова входит в FIFO-очередь.

### Handoff между чатами

Каждый новый чат перед работой полностью читает
`CoordinationRuntime/HANDOFF.md`, а затем проверяет важные утверждения по
текущим файлам и `git status`. Перед освобождением lock он добавляет запись:

```markdown
## <UTC time> — <agent_id> — <status>

Task: <кратко>

Changed:
- <точный путь>: <что и зачем>

Validation:
- <команда или ручная проверка>: <результат>

Pending / risks:
- <остаток или none>

Suggested next step:
- <следующее действие или none>
```

Чужие записи не переписываются и не удаляются. В журнал не помещаются секреты,
большие логи и дампы сгенерированных файлов.

### Зависший lock

Heartbeat старше десяти минут делает lock подозрительным, но не разрешает
удалять его автоматически. Сначала необходимо проверить `owner.md`, заявку и
agent-запись, активные Unity/build/shell-процессы, заявленные файлы и
`git status`. Если владелец явно не помечен как `completed`, `yielded`,
`blocked` или `abandoned`, удаление чужого lock требует подтверждения
разработчика.

## Экономное ожидание

- Предпочитать событийное ожидание, если среда его поддерживает.
- По умолчанию без событий выполнить одну повторную проверку через осмысленный
  интервал. Если очередь по-прежнему занята, завершить текущий ход и назвать
  владельца.
- По явному запросу пользователя разрешено продолжительное ожидание: без
  удержания `write-lock`, с интервалом проверки не менее 60 секунд и общим
  таймаутом не более 10 минут.
- За один период продолжительного ожидания выполняется не более 10 проверок.
  Если очередь не освободилась, поток завершает текущий период polling,
  сохраняет свою заявку в FIFO и повторно проверяет основание ожидания.
- Если пользователь явно потребовал «не останавливаться», «дождаться и
  продолжить» или задал другое терминальное условие, поток не завершает задачу
  после десятиминутного периода. Без удержания `write-lock` он автоматически
  начинает следующий ограниченный период ожидания, пока владелец показывает
  прогресс или корректный heartbeat.
- После освобождения ресурса ожидающий поток без нового сообщения пользователя
  повторно проверяет `HANDOFF.md`, свою позицию FIFO и актуальный `git status`,
  получает `write-lock` в обычном порядке и продолжает исходную задачу.
- Непрерывное ожидание прекращается только при достижении результата либо при
  реальном блокере, требующем нового пользовательского решения, внешнего
  доступа или разрешения. Сам факт занятой очереди или долгой сборки таким
  блокером не считается.
- При повторной проверке читать только `active/`, сортированный список
  `requests/` и запись владельца.
- Не публиковать повторяющиеся сообщения о неизменившейся блокировке.

## Безопасность памяти и процессов

Каждый чат работает последовательно: не запускает несколько команд
одновременно, фоновые jobs, параллельные worker-пулы или несколько терминальных
сессий для одной задачи. Внутренние субагенты не используются для работы с этим
репозиторием.

Для проекта одновременно допускается не более одного тяжёлого процесса. К ним
относятся Unity Editor и batch mode, импорт ассетов, сборки, тесты, генераторы,
индексация IDE, упаковка архивов и массовая обработка контента. Перед запуском
проверяются и runtime-очередь, и реальные процессы ОС. Если инструмент
поддерживает ограничение workers/jobs, используется один worker.

Лёгкий независимый read-only анализ в пользовательских чатах может выполняться
одновременно, если он не запускает Unity, не импортирует ассеты и не создаёт
сгенерированные файлы.

## Матрица владения

### Shared pipeline

Основная область:

- `Packages/NovelsContentSdk/**`;
- `Tools/novels-tools/**`;
- `Novels/Docs/AI/ContentPipeline.md`;
- общие JSON-контракты и формат `release.json`.

Этот поток не должен массово переименовывать или пересериализовывать контент
историй.

### Catalog

Основная область:

- `Projects/novels-catalog/**`.

Не меняет SDK-контракты самостоятельно. Если для каталога требуется изменение
контракта, оно сначала фиксируется в статус-файле, затем переносится владельцем
shared pipeline.

### TZM

Основная область:

- `Projects/novels-tzm/**`.

Разрешены локальные исправления ассетов, Ink, definition и prefab. Общие
исключения не следует добавлять непосредственно в SDK без согласования.

### ZDM

Основная область:

- `Projects/novels-zdm/**`.

Правила те же, что для TZM: проектные особенности остаются данными проекта, а
не превращаются в глобальный hardcode.

### Game

Основная область:

- `Novels/Assets/Novels/**`;
- Player build и runtime-интеграция контента.

Game не должен снова получать authoring-контент, собственный bundle-builder или
копию валидатора из Content SDK.

## Зафиксированный общий контракт

Пока отдельное согласованное изменение не описано в статус-файле pipeline,
действуют следующие правила:

1. Один атомарный Unity-проект производит один bundle на выбранную платформу.
2. AssetBundle labels вручную не назначаются.
3. Story-конфигурация хранится в `Config/card.json`.
4. Catalog-конфигурация хранится в `Config/catalog.json`.
5. `minimumClientVersion` находится в соответствующем основном JSON.
6. Отдельного `Config/build.json` нет.
7. Поддерживаемые цели CLI: `editor`, `android`, `ios`.
8. Compose выполняется внутри команды `build`.
9. Валидация собирает все найденные проблемы за один проход.
10. Предупреждения и ошибки группируются в отдельные сообщения.

Публичные команды:

```bash
Tools/novels-tools/novels-content doctor
Tools/novels-tools/novels-content validate <catalog|story-id|all>
Tools/novels-tools/novels-content build <catalog|story-id|all> <editor|android|ios>
Tools/novels-tools/novels-content publish <destination-directory>
```

## Что нельзя делать параллельно

- Запускать два Unity Editor или две bundle-сборки одновременно.
- Массово переименовывать общие пути, пока другой поток валидирует проект.
- Запускать миграцию всех контентных проектов из одного чата.
- Очищать `Library`, Build или кеши соседнего проекта без необходимости.
- Делать общий `git reset`, `checkout --`, `clean` или удалять незнакомые файлы.
- Коммитить все изменения рабочего дерева одной командой без проверки области.

Тяжёлые операции выполняются последовательно, особенно для TZM и ZDM.

## Протокол изменения общего контракта

Если контентному проекту не хватает общего API:

1. Не добавлять локальную копию SDK-кода.
2. Описать проблему и ожидаемый контракт в статус-файле проекта.
3. Перечислить затрагиваемые файлы и примеры входных данных.
4. Внести общее изменение в потоке shared pipeline.
5. Сначала проверить каталог или маленький fixture.
6. Затем последовательно проверить TZM и ZDM.
7. Зафиксировать результат в `ParallelWork.pipeline.md`.

## Передача результата на интеграцию

Поток со статусом `ready-for-integration` должен указать:

- базовый и итоговый commit, если commit создавался;
- полный список изменённых путей;
- новые, удалённые или изменённые контракты;
- выполненные команды проверки;
- известные предупреждения;
- обязательные действия после merge;
- можно ли безопасно повторно импортировать проект.

Фраза «всё работает» без этих данных не считается достаточной передачей.

## Итоговая интеграция

После завершения соседних потоков выполняется только один последовательный
интеграционный проход:

1. Сопоставить статус-файлы и найти пересечения путей.
2. Проверить отсутствие возвращённых `build.json` и AssetBundle labels.
3. Проверить общий SDK и CLI.
4. Выполнить `doctor`.
5. Выполнить `validate catalog`, затем `tzm`, затем `zdm`.
6. Собрать Catalog для Editor как лёгкую проверку bundle pipeline.
7. Собрать TZM и ZDM для Editor строго последовательно.
8. После этого собрать `all android` и `all ios`.
9. Проверить runtime Game и публикацию серверного дерева.
10. Перевести статус-файлы в `integrated` или удалить их отдельным cleanup-коммитом.

## Текущее состояние shared pipeline

На момент создания документа в рабочем дереве выполняется упрощение общего
pipeline:

- `AtomicContentBuild` превращён в тонкую Unity-точку входа;
- pipeline и накопительный validation report вынесены в Content SDK;
- сборка принимает одну платформу;
- bundle строится явным `AssetBundleBuild`;
- `minimumClientVersion` перенесён в `card.json`/`catalog.json`;
- compose стал внутренним этапом `build`;
- Catalog, TZM и ZDM прошли последовательную Unity-валидацию;
- тестовая Editor-сборка Catalog прошла успешно.

До интеграции соседних потоков shared pipeline не должен массово менять
внутреннее содержимое `Projects/novels-*`.
