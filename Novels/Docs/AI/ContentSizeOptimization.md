# Оптимизация размера атомарных историй

Цель — уменьшить доставляемый и установленный контент без незаметной смены
авторского материала, нарушения адресации или ухудшения визуального качества.
Исходные цифры находятся в `ContentSizeBaseline.md`.

## Порядок работ

### 1. Автоматический отчёт

Ожидаемая общая команда pipeline:

```bash
Tools/novels-tools/novels-content size <story-id|all>
```

Она должна читать source tree и существующие `release.json`, выводить размеры
bundle/payloads по платформам, вклад типов файлов, крупнейшие файлы, точные
дубликаты и delta к зафиксированному baseline. Реализация принадлежит shared
pipeline; story-проекты не должны получать локальные копии этого инструмента.

### 2. Точные дубликаты

Для каждой SHA-256-группы:

1. Проверить назначение и import settings всех копий.
2. Проверить использования в Ink и serialized assets.
3. Выбрать канонический ID.
4. Если ID должен сохраниться, использовать поддержанный alias, а не копию.
5. Если ресурс используется несколькими эпизодами, перенести его в `shared`
   только после подтверждения, что runtime умеет разрешать этот тип из shared.
6. Удалять копии отдельным небольшим изменением и пересобирать одну историю.

Автоматическое удаление запрещено. Первую партию следует ограничить 3–5
крупными location-дубликатами `zdm`: там нет видео и проще увидеть эффект.

### 3. Texture profiles

Профиль выбирается по семантическому пути:

| Категория | Mipmaps | Read/Write | Начальный Max Size | Экспериментальный формат |
| --- | --- | --- | ---: | --- |
| location | off | off | 2048 | ASTC 6x6, затем 8x8 |
| character body/clothes | off | off | 2048 | ASTC 4x4 или 6x6 |
| emotion/accessory | off | off | 1024–2048 | ASTC 4x4 или 6x6 |
| choose item | off | off | 512–1024 | ASTC 6x6 |
| presentation UI | off | off | по фактическому размеру | ASTC 4x4 |

Таблица — старт эксперимента, не утверждённый production-контракт. Для Mac
нужен отдельный desktop-профиль. Crunch включается только после измерения
размера и времени загрузки.

`NovelContentTextureImporter` должен оставаться единственным владельцем общей
политики. Изменение передаётся потоку shared pipeline и сопровождается тестами
классификации путей.

### 4. Визуальный quality gate

До массового реимпорта выбрать фиксированный набор:

- тёмный location из `zdm`;
- большой яркий location из `zdm`;
- подводный градиент из `tzm`;
- персонаж с полупрозрачными краями волос;
- лицо и эмоция;
- одежда и аксессуар;
- presentation UI;
- крупнейшее, динамичное и почти статичное видео `tzm`.

Для каждой платформы сравнить исходник и импортированный результат на целевом
разрешении. Проверяются banding, alpha fringe, детали лица, текст, looping seam,
время загрузки и память. Без этого массовое изменение `.meta` не принимается.

### 5. Видео TZM

Для 51 MP4 сначала собираются разрешение, FPS, длительность, codec, bitrate,
аудиодорожки и использование в Ink. Первая проба включает:

- самый большой файл (`причал.mp4`);
- динамичную сцену;
- почти статичный фон.

Возможные действия: удалить ненужное аудио, снизить FPS фоновых циклов,
ограничить разрешение фактическим экраном и подобрать bitrate. H.264 остаётся
безопасным baseline; HEVC допустим только после проверки поддержки всех
клиентов. Перекодированный файл принимается после визуального сравнения и
проверки бесшовного цикла.

### 6. Production payloads

Нужно подтвердить потребителей следующих файлов:

- корневой и episode source `.ink`;
- compiled `.ink.json`;
- source map;
- дополнительный `<id>.json`.

До проверки Game ничего не исключается. Целевая архитектура может разделить
runtime payloads и diagnostic artifacts, но это изменение release-контракта и
требует владельца shared pipeline и Game.

### 7. Неиспользуемые assets

Поскольку текущий `AssetBundleBuild` включает весь `Assets/RemoteAssets`, любой
забытый файл увеличивает bundle. Анализ должен классифицировать asset как
`used`, `indirect`, `fallback`, `unused` или `unresolved`. Динамически
адресуемые ресурсы требуют allowlist. Удаление выполняется только после отчёта
с точными путями и повторной валидации.

### 8. Size budgets

До первой оптимизации бюджеты работают как warning и фиксируют регрессии.
После двух стабильных сборок утверждаются отдельные лимиты для:

- bundle каждой платформы;
- всех payloads;
- одного PNG source;
- одного MP4;
- недельной или PR-delta.

CI должен показывать абсолютную delta, процент и крупнейшие добавленные assets.
Не следует назначать лимит ниже текущего baseline до подтверждённой оптимизации.

### 9. Episode bundles — только при необходимости

Разделение одного story bundle на shared и episode bundles уменьшит стартовую
загрузку, но изменит зафиксированный архитектурный контракт, delivery groups,
кеш и Game runtime. Решение рассматривается только после дубликатов, texture
profiles, видео и unused assets. Оно оформляется отдельным design proposal.

## Acceptance criteria первой итерации

- baseline воспроизводится из существующих или новых `release.json`;
- полный список exact duplicates доступен машинно;
- выбрана небольшая безопасная партия дубликатов `zdm`;
- один texture profile проверен визуально на Android и iOS;
- три видео `tzm` имеют измеренные варианты с delta и quality verdict;
- новая сборка каждой истории проходит validate и создаёт один bundle;
- размер не вырос ни на одной платформе;
- status-файлы содержат точные команды и результаты.
